# upsguard — спецификация текущей реализации

Обновлено 2026-09-30 по коду `upsguard/upsguard.py`, обоим INI, установщику и службам. Имя файла сохранено для существующих ссылок. Руководство по установке — в `README.md`; образцы настроек — в `conf/`.

## 1. Задача и подтверждённые данные

Delta GAIA 3 кВА питает АРМ1, АРМ2 и сетевое оборудование. АРМ1 `sikn-531` с Astra Linux 1.8 связан с ИБП по USB; АРМ2 получает показания от NUT на АРМ1 по сети. Программа управляет только своим АРМ и его монитором.

Подтверждено ранее на АРМ1:

- USB VID/PID: `05dd:041b`.
- NUT 2.8.1 установлен; `nut-server.service` работает.
- Имя рабочей секции NUT — `delta`; команда чтения — `upsc delta@localhost`.
- Снятые показания: `OL`, заряд 100 %, остаток 7239 с, нагрузка 10 %, мощность 202 Вт. Это исторический снимок, а не текущие значения.
- `rtcwake -m off -s 120` выключил АРМ1 и включил его через две минуты.
- Пользователь подтвердил вход в гибернацию `disk`. Для `mem` доступен только `s2idle`: `freeze` даёт тот же результат, а `standby` в `/sys/power/state` отсутствует. Вход в гибернацию не заменяет отдельную проверку RTC-восстановления.
- Для `nut-scanner -U` на этой сборке потребовался `libusb-1.0-0-dev`. В комплекте 11 пакетов с `MANIFEST.tsv` и `SHA256SUMS`.

Режимы сна, физическое гашение мониторов и совместный цикл обоих АРМ требуют испытания на площадке.

## 2. Чтение показаний и действия

| Узел | Источник свежих показаний | Исполняемое действие |
|---|---|---|
| АРМ1, `role = master` | Физическая проверка USB до и после локального `upsc` | RTC, выключение/сон или монитор только АРМ1 |
| АРМ2, `role = client` | NUT `LIST VAR` по TCP/3493 на АРМ1 | RTC, выключение/сон или монитор только АРМ2 |

Клиенту не нужны NUT, USB, SSH-ключи или команда выключения от мастера. Каждый АРМ принимает решение по своему INI. Нагрузка, мощность и остаток времени выводятся для диагностики; условия действия задаются процентом заряда и статусом `LB`.

Программа не отправляет команды в ИБП. На АРМ1 установщик маскирует `nut-monitor.service` и прекращает установку при наличии `/etc/killpower`. Он не удаляет этот флаг автоматически и не переписывает конфигурацию NUT.

## 3. Выбор действия одним параметром

`[general] action_mode` — основной переключатель. В обоих поставляемых INI стоит `off`.

| Значение | Фактическое действие |
|---|---|
| `off` | `rtcwake -m off -s <wake_interval>`: будильник и штатное выключение |
| `mem` | `rtcwake -m mem -s <wake_interval>`: сон с сохранением памяти |
| `disk` | Гибернация через `rtcwake -m disk`, если она работает на АРМ |
| `standby`, `freeze` | Соответствующий режим сна через `rtcwake` |
| `monitor_only` | X11 DPMS или консольный framebuffer; RTC не вызывается |
| `no` | Дополнительный вариант: `rtcwake -m no`, затем `systemctl poweroff` |

Произвольная shell-команда в конфиге не исполняется. При ошибке команды RTC выключение через `systemctl` не выполняется. Для сна вызов `rtcwake` ждёт возвращения после пробуждения без короткого таймаута.

Совместимость со старыми настройками:

- `action_mode = poweroff` без `rtc_mode` означает прежний режим `no`; со старым `rtc_mode = no/off` сохраняет выбранный вариант.
- `action_mode = sleep` со старым `rtc_mode = mem/disk/standby/freeze` сохраняет выбранный сон; без него используется `mem`.
- При новом `action_mode = off/mem/disk/standby/freeze/no/monitor_only` старая строка `rtc_mode` игнорируется. В новых INI её нет.

## 4. Политика во время работы

1. `OB` подтверждается непрерывно в течение `ob_debounce`.
2. Для выключения/сна заряд должен быть **не выше** `charge_percent` непрерывно в течение `trigger_hold`. Затем начинается `shutdown_grace`.
3. `LB` при подтверждённом отключении запускает `lb_grace`. Если другой отсчёт закончится раньше, его срок не продлевается.
4. Устойчивый `OL` в течение `ol_stable` отменяет ожидающее действие.
5. Отсутствие свежих данных отменяет отсчёт. В режиме мониторов оно также возвращает экран, погашенный этой программой.
6. Непосредственно перед действием выполняется повторный запрос; без свежего `OB` действие отменяется.

В `monitor_only` монитор гасится после подтверждения `OB` независимо от процента заряда; гашение повторяется через `refresh_interval`. После устойчивого `OL` или остановки службы программа возвращает погашенный ею экран.

Возврат заряда выше порога сам по себе не отменяет уже начатый отсчёт. При перезапуске процесса с тем же действием сохранённый отсчёт продолжается. Смена `action_mode` сбрасывает срок и запускает новое подтверждение порога и задержку. Старое состояние без сохранённого `action_mode` также не переносит прежний срок.

## 5. RTC-пробуждение

Перед реальным действием в состояние записывается маркер `powered_off_by_policy`. Основная служба при запуске сначала обрабатывает его функцией `boot_check`, затем запускает обычный мониторинг. После сна та же проверка выполняется в продолжающем работу процессе. `Type=simple` позволяет рабочему столу стартовать во время проверки RTC-загрузки.

- Устойчивый `OL` снимает маркер и разрешает нормальную работу.
- Подтверждённый `OB` начинает новый отсчёт `shutdown_grace`, затем следует ещё один запрос и повторное действие. При этой проверке процент заряда уже не определяет повторное действие.
- Если свежих данных с начала проверки нет 60 с, АРМ остаётся включённым. Если данные появлялись, но устойчивый `OL`/повторный `OB` подтвердить не удалось, проверка завершается через `boot_check_timeout` с тем же результатом.
- После повторного сна начинается новый цикл проверки. Интервал до RTC-будильника отсчитывается при вызове команды, после паузы перед действием.

Выключенный или спящий АРМ1 не опрашивает USB и не обслуживает NUT-клиента. Поэтому немедленное включение при переходе ИБП в `OL` не предусмотрено: ИБП проверяется при следующем RTC-пробуждении.

Синхронизация двух АРМ и WoL не реализованы. Если АРМ2 проснулся без доступного АРМ1, отсутствие данных оставит его работающим. Таким образом, строго общий повторный цикл двух АРМ пока не гарантирован.

## 6. Конфигурация и проверка значений

Рабочий файл — `conf/upsguard.ini` в папке программы (например, `~/upsguard/conf/upsguard.ini`). Он читается как UTF-8 один раз при запуске; образцы содержат русское пояснение над каждым параметром. Путь по умолчанию определяется относительно файла программы, а не текущего каталога; `--config` переопределяет его для ручного запуска. CLI и журнал запуска показывают полный путь INI.

| Секция | Параметр | Поставляемое значение |
|---|---|---|
| general | role | master; в образце АРМ2 — client |
| general | action_mode | off |
| general | dry_run | yes |
| general | wall | yes |
| general | state_file | /var/lib/upsguard/state.json |
| general | log_file | /var/log/upsguard.log |
| nut | ups | delta@localhost; в образце АРМ2 — delta@MASTER_IP |
| nut | poll_interval | 2 с |
| nut | query_timeout | 5 с |
| policy | charge_percent | 50 % |
| policy | trigger_hold | 20 с |
| policy | ob_debounce | 5 с |
| policy | ol_stable | 30 с |
| policy | shutdown_grace | 120 с |
| policy | lb_grace | 120 с |
| policy | wake_interval | 900 с |
| policy | boot_check_timeout | 240 с |
| policy | comms_notify_after | 60 с |
| display | backend | auto |
| display | popup | yes |
| display | name | :0 |
| display | xauthority | пусто |
| display | refresh_interval | 30 с |

`check-config` отвергает неизвестные секции/параметры и неподдерживаемые режимы. Основные ограничения:

- `charge_percent` от 0 до 100; числовые интервалы должны быть конечными и неотрицательными.
- `poll_interval` и `query_timeout` не меньше 1 с; `refresh_interval` не меньше 5 с.
- `shutdown_grace` не меньше 60 с и не меньше `ol_stable + 15`.
- `wake_interval` не меньше 180 с.
- `boot_check_timeout` должен вмещать `shutdown_grace + ob_debounce + poll_interval`.
- Мастер опрашивает локальный NUT, клиент указывает удалённый адрес. Файлы состояния/журнала и непустой `xauthority` имеют абсолютные пути.

При `dry_run = yes` продолжаются опрос, политика, логирование и запись диагностического состояния; команды RTC, выключения/сна и управления монитором не исполняются. При переключении на `no` сохранённый истёкший отсчёт может сработать после свежего подтверждения `OB`.

`status` показывает новый опрос и содержимое INI на диске. Он не перечитывает настройки уже работающего процесса. После правки нужны `check-config` и `systemctl restart upsguard.service`.

## 7. Состояние, сообщения и экран

Основная логика находится в `upsguard/upsguard.py`, графический процесс — в `upsguard/desktop.py`:

| Компонент | Что делает |
|---|---|
| `load_config`, `Config` | Чтение UTF-8 INI, совместимость и проверки |
| `read_ups`, `read_nut_socket` | Локальный upsc или сетевой LIST VAR |
| `Policy.step` | Порог, подтверждения статусов и отсчёт |
| `StateStore` | Атомарная запись JSON с правами 0600 |
| `power_action` | Локальная команда RTC и, в режиме no, poweroff |
| `DisplayControl` | X11 DPMS либо /sys/class/graphics/fb0/blank |
| `DesktopAlert`, `desktop.py` | Окно X11, заряд, секундный таймер, запрос остановки |
| `boot_check`, `monitor` | Проверка после действия и основной цикл |

Таймеры в процессе используют `time.monotonic()`. Состояние хранит `version`, `boot_id`, объект `policy` с `action_mode`, началом отключения, сроком, причиной и флагами, а также маркер `powered_off_by_policy`. При другом `boot_id` прежняя политика не восстанавливается; маркер используется для проверки загрузки. Пригодность сохранённых времён ограничена семью сутками.

Лог пишется в stdout/journald и файл, с ротацией 1 МиБ и пятью копиями. Сообщения терминала и установщика — ASCII; русские INI, документация и графическое окно — UTF-8. Терминальные уведомления выполняются через `wall`, если это разрешено конфигом.

При `display.popup = yes` и доступном X11 отдельный процесс рисует русское окно через libX11/libcairo. Python-пакеты и файлы обмена не требуются: данные передаются JSON через неблокирующие каналы. Срок берётся из текущего решения политики; окно обновляет секундный таймер самостоятельно. Кнопка остановки только сообщает основному процессу запрос: тот отменяет решение, очищает состояние и посылает `systemctl --no-block stop` для обеих локальных служб. Крестик и «Скрыть окно» не отменяют действие. Потеря свежих показаний и устойчивый OL закрывают окно. Ошибка команды в основном цикле отображается вместе с повторной попыткой через 30 с. `monitor_only` не открывает окно.

Команда `test-popup` показывает демонстрацию на 30 с: не опрашивает ИБП, не захватывает блокировку службы и не выполняет команды RTC/питания/остановки. При недоступном X11 возвращает ошибку. Если X11 ещё не запущен или авторизация не подходит, служба сохраняет штатную политику и повторяет попытку открыть окно раз в 15 с.

`backend = auto` выбирает X11 при наличии сокета выбранного дисплея, иначе framebuffer. Для X11 используются `name`, заданный или найденный `Xauthority` и утилита `xset`. Настройки DPMS целиком не сохраняются: программа только выполняет `force off/on`.

## 8. Установка и службы

- `install.sh --role master`: требует работающий NUT/upsc на АРМ1.
- `install.sh --role client --master-ip <IPv4_АРМ1>`: задаёт роль и IP в том же `conf/upsguard.ini`; пакеты NUT не нужны. Имя секции ИБП сохраняется. При переводе клиента в мастер адрес становится локальным.
- Код и INI остаются в папке проекта. Шаблоны служб получают абсолютные пути к этой папке и устанавливаются в `/etc/systemd/system`. `RequiresMountsFor` связывает запуск с доступностью файловой системы папки.
- Параметры действия, `dry_run`, комментарии и владелец INI сохраняются. Изменения роли/IP сначала валидируются, затем атомарно записываются в рабочий файл. При распаковке обновления пользователь должен исключить свой рабочий INI из замены.
- Старые копии кода/INI в `/opt/upsguard` и `/etc/upsguard` не используются; они не удаляются автоматически. После переноса папки требуется повторить установку для смены путей в службах.
- Скрипт не устанавливает .deb, не меняет NUT LISTEN и не открывает файрвол. На мастере проверяется `MAXAGE`, если он задан: не больше 30 с.
- Установщик отключает автозапуск и останавливает старый boot-check, затем включает и перезапускает основную службу. Внутри неё `boot_check` и мониторинг выполняются последовательно под одной блокировкой.

`upsguard.service`: `Type=simple`, команда `run` (проверка RTC, затем мониторинг), `Restart=on-failure`, пауза 5 с. Штатный выход после отмены пользователем не вызывает перезапуск. Основная служба не зависит от отдельного юнита boot-check и не задерживает старт рабочего стола на время отсчёта. `upsguard-bootcheck.service`: отключённый от автозапуска `Type=oneshot`, сохранён для ручной проверки при остановленной основной службе; `TimeoutStartSec=infinity` допускает повторные циклы сна. Внутри каждой проверки действует `boot_check_timeout`.

Обе службы работают от root и пользуются общей блокировкой, чтобы не управлять одним АРМ одновременно. На клиенте отсутствующая служба NUT не является обязательной зависимостью.

`uninstall.sh` останавливает/отключает службы и удаляет системные юниты. Папка программы, INI, состояние и журнал остаются. Маска `nut-monitor` также сохраняется.

## 9. Проверки и ограничения поставки

Проверки разработки: `python3 -m unittest discover -s tests -v`, проверка синтаксиса Python/shell и `systemd-analyze verify`. Тесты используют имитацию RTC и показаний; они не выключают настоящие АРМ.

На площадке нужно подтвердить чтение на обоих АРМ, отмену при USB/сетевой потере, возврат OL, физическое действие выбранного RTC-режима и мониторов. Отдельно проверяется доступность АРМ1 при пробуждении АРМ2.

Клиент узнаёт о пропаже USB через свежесть данных NUT: возможен короткий промежуток, пока сервер ещё отдаёт прежние значения. Остаётся также промежуток между последним успешным запросом и действием. Поэтому опрос по сети не даёт абсолютной мгновенной гарантии физического USB-подключения.

В поставке отсутствуют дополнительные условия выключения по длительности отключения или остаточному времени, команда simulate, полноценная панель управления, WoL и управление выходами ИБП. Эти функции из раннего плана не должны использоваться как описание текущей программы.
