# upsguard — дизайн

Дата: 2026-09-29. Статус: согласован в диалоге по частям, ждёт ревью пользователя.

## 1. Задача

ИБП Delta GAIA 3 кВА (GES302R2RT2B035) питает АРМ на Astra Linux и сетевое оборудование, которое должно жить дольше ПК. Батареи не хватает на ~2 часа при реальной нагрузке. При работе от батареи ПК должен:

1. гасить монитор;
2. штатно выключаться: через заданное время T или раньше, если батарея слабая;
3. **не трогать питание ИБП**: сэкономленная батарея нужна сетевому оборудованию;
4. (фаза 2) сам включаться после возврата сети.

## 2. Границы

**Фаза 1:** чтение состояния ИБП, лестница реакций (уведомление, монитор, выключение), лог, `dry_run`, офлайн-упаковка, тесты.

**Фаза 2:** автовозврат ПК по RTC-будильнику.

**Не делаем:** трей и GUI, управление группами розеток LOAD 1/2 (по USB недоступно, см. п. 3), любые команды в ИБП, e-mail и SNMP-уведомления, несколько ИБП, несколько ПК на одном ИБП (схема master/slave у NUT).

## 3. Факты и допущения

### Установлено по документации и исходникам (на железе не проверено)

- NUT поддерживает Delta RT и Amplon R 1/2/3 кВА драйвером `usbhid-ups` с подпрограммой `delta_ups-hid` (VID `05dd`, PID `041b`). DDL-дамп UPS302R2000B0BA снят на NUT 2.7.4. В нём есть `ups.status`, `battery.charge`, `battery.runtime`, `ups.load`, `ups.realpower`, `battery.charge.low` (rw), `ups.delay.start`, `ups.start.auto`.
- В том же дампе нет ни одной `outlet.*`: группами розеток по USB управлять нельзя.
- Мануал GAIA 1–3 кВА: USB; DB9 (RS-232 2400 8N1 и сухие контакты Utility Fail, Low Battery, Remote Shutdown); слот SNMP (с картой RS-232 недоступен); EPO; разъём внешних батарей; две группы розеток LOAD 1/2.
- Мануал соседней RT-серии: функция «Battery Save». ИБП сам выключается после 30 минут на батарее при очень малой нагрузке. В мануале GAIA такого нет.

### Не проверено (выясняется в фазе 0)

- PID модели и то, что USB у неё HID. У части Delta Amplon «USB» оказывается UART-мостом (CH341 `1a86:5523`, XR21V1410 `04e2:1410`); `usbhid-ups` такие устройства не видит.
- Версия NUT в репозитории Astra (ожидается 2.7.4, как в Debian 10).
- Реальные значения `ups.status`, `battery.charge`, `battery.runtime`, `ups.load` на этом ИБП.
- Поведение «Battery Save» на GAIA.
- Поддержка RTC-пробуждения в BIOS ПК.
- Управляемость DPMS под Fly и Astra SE.

## 4. Архитектура

```
ИБП ──USB──> usbhid-ups ──> upsd (127.0.0.1:3493) <── upsguard (наш демон)
              (NUT)          (NUT)                     ├─ гасит монитор
                                                        ├─ выключает ПК
                                                        └─ лог / уведомления
```

- **NUT только читает ИБП:** работают `usbhid-ups` и `upsd`. Юнит `upsmon` (в Debian `nut-monitor.service`) маскируется, флага `POWERDOWNFLAG` (по умолчанию `/etc/killpower`) быть не должно. Поэтому NUT никогда не отключит выход ИБП.
- **`upsguard` единственный «выключатель».** Демон под systemd от root (без `User=`), Python 3.7, только stdlib. С `upsd` говорит по текстовому протоколу и **только читает**. Команд в ИБП не шлёт. Страховочный `upsmon` по Low Battery сознательно не используется: он отрубил бы весь выход ИБП вместе с сетью.
- Все внешние вызовы (сокет, `subprocess`) идут с таймаутами. Остановка по SIGTERM через `threading.Event`: под systemd stdin не терминал, `input()` использовать нельзя (урок upsmonitor).

### Модули

| Модуль | Назначение | Интерфейс |
|---|---|---|
| `nutclient` | Протокол `upsd`: подключение, таймауты, переподключение | `NutClient(host, port, timeout).get_vars(ups) -> dict[str, str]`; бросает `NutError`. Отправляет только `LIST VAR`. |
| `policy` | Чистая логика без ввода-вывода | `Policy(config).step(sample, now) -> list[Action]`; `to_dict()`/`from_dict()` для состояния. `sample`: `Sample(status: frozenset, charge, runtime, load)` или `None` (нет связи). `now`: монотонные секунды. Виды `Action`: `Notify(kind, text)`, `BlankMonitor`, `RestoreMonitor`, `Poweroff(reason)`; в фазе 2 добавится `ArmWake(seconds)`. |
| `actions` | Побочные эффекты | `MonitorControl.blank()/restore()`, `Power.poweroff(reason)`, `Notifier.send(kind, text)`; каждый принимает `dry_run` и обёртку `runner` над `subprocess` (для тестов). |
| `daemon` | Цикл: опрос, `policy.step`, выполнение действий, сохранение состояния | `run(config)` |
| `config` | INI в dataclass с проверкой диапазонов | `load(path)` |
| `cli` | Команды | `run` (по умолчанию), `status`, `check-config`, `simulate <сценарий.json>` |

`simulate` прогоняет ряд отсчётов через `policy` с фейковыми часами и печатает хронологию действий. С его помощью можно подобрать T, не выдёргивая вилку.

## 5. Политика (фаза 1)

### Сигналы

Каждые `poll_interval` (2 с) из `upsd` читаются `ups.status` (токены `OL`, `OB`, `LB`, `RB`), `battery.charge`, `battery.runtime`, `ups.load`, `ups.realpower`.

### Что считать отключением

- `OB` держится не меньше `ob_debounce` (5 с): началось отключение. Момент начала это первый `OB` этой серии, а не конец дебаунса.
- Отключение закончилось, когда `OL` держится не меньше `ol_stable` (30 с). Мигающая сеть это одно длинное отключение, таймеры не сбрасываются.

### Лестница (время от начала отключения)

| Когда | Что делаем |
|---|---|
| Начало | Лог и уведомление: «работаем от батареи, выключение примерно через X мин» |
| `monitor_off_after` (120 с) | Гасим монитор |
| Любое из правил: `shutdown_after` (T, 2700 с), `battery.charge` ≤ `shutdown_at_charge` (25 %), `battery.runtime` ≤ `shutdown_at_runtime` (600 с) | Предупреждение, через `shutdown_grace` (90 с) штатное выключение |
| `LB` во время отключения | Выключение через `lb_grace` (10 с). Если предупреждение уже идёт с более поздним сроком, срок сокращается. |

- Правила по заряду и остатку срабатывают, только если условие держится `trigger_hold` (20 с) подряд, а значения свежие (получены в текущем опросе, не отрицательные). Это защита от кратковременных плохих показаний сразу после переключения на батарею.
- Каждое числовое правило можно отключить значением `off`.
- Сеть вернулась до выключения: когда отключение объявлено закончившимся (стабильный `OL`, `ol_stable`), таймеры отменяются, монитор восстанавливается, приходит уведомление. Если в этот момент идёт предупреждение, выключение тоже отменяется. Поэтому `shutdown_grace` должен быть заметно больше `ol_stable`: реальное окно отмены равно `shutdown_grace − ol_stable` (60 с при значениях по умолчанию). `check-config` требует `shutdown_grace ≥ ol_stable + 15`. После вызова `poweroff` отмена невозможна. При `LB` выключение не отменяется.
- Во время отключения раз в 60 с в лог пишутся `charge`, `runtime`, `load`, `realpower`: по ним подбирается T. Флаги `RB` и `ALARM` пишутся в лог при появлении.

### Потеря связи с ИБП

- В штатном режиме: `WARNING` в лог сразу, одно уведомление через `comms_lost_notify_after` (60 с) непрерывной потери, ничего не выключаем.
- Во время отключения: таймер T продолжает идти, так как от данных ИБП не зависит. Правила по заряду и остатку при отсутствии данных не срабатывают. Выключение по времени сработает даже без связи.

### Состояние на диске

`/var/lib/upsguard/state.json`, запись атомарная (временный файл и `os.replace`):

```json
{
  "version": 1,
  "boot_id": "<содержимое /proc/sys/kernel/random/boot_id>",
  "outage_started_epoch": 1790000000.0,
  "monitor": {"blanked": true, "saved_dpms": {"enabled": true, "standby": 600, "suspend": 600, "off": 600}},
  "shutdown": {"issued_epoch": null, "reason": null},
  "powered_off_by_policy": {"epoch": null, "reason": null}
}
```

- Таймеры внутри процесса считаются по `time.monotonic()`. Эпоха нужна только для восстановления после перезапуска демона. Если она в будущем или старше 7 суток, состояние отбрасывается.
- Состояние отключения и монитора отбрасывается, если `boot_id` не совпадает с текущим (ПК перезагружался). `powered_off_by_policy` переживает перезагрузку: в фазе 1 при старте оно пишется в лог как «предыдущее выключение сделано политикой upsguard» и очищается, в фазе 2 по нему работает автовозврат.
- Перезапущенный демон при `OB` продолжает отключение с восстановленным началом. При `OL` остаётся в состоянии отключения, пока `OL` не продержится `ol_stable`.

## 6. Действия

### Монитор (X11)

1. **Поиск дисплея.** По `/proc/*/cmdline` находим процессы `X`/`Xorg`, из аргументов берём номер дисплея (`:N`) и файл после `-auth`. Запасной путь: `loginctl` (сессии типа `x11`, `~user/.Xauthority`).
2. **Запуск.** От root вызываем `xset` с `DISPLAY` и `XAUTHORITY`, поэтому не важно, кто залогинен.
3. **Сохранение настроек.** Разбираем вывод `xset q` (DPMS on/off, `Standby/Suspend/Off`) и кладём в `state.json`.
4. **Гашение.** `xset +dpms`, `xset dpms <idle> <idle> <idle>` (`idle_off_seconds`, 60 с), `xset dpms force off`. Экран гаснет один раз, дальше сам гаснет через минуту бездействия, оператор может разбудить его мышью.
5. **Восстановление.** `xset dpms <standby> <suspend> <off>` с сохранёнными значениями, `xset +dpms` или `xset -dpms` по сохранённому флагу, затем `xset dpms force on`.
6. **Нет X-сессии.** Пропускаем, пишем в лог.
7. **`dry_run`.** Команды пишутся в лог, но не выполняются.

### Выключение

Предупреждение (лог и уведомления), `shutdown_grace`, затем `systemctl poweroff`. В `state.json` пишутся `shutdown.issued_epoch`, `shutdown.reason` и `powered_off_by_policy`. При `dry_run` в лог пишется «выключил бы», `powered_off_by_policy` не записывается, а остальное состояние ведётся как обычно, так что лестницу можно наблюдать целиком.

### Уведомления

- Лог всегда: stdout (journald) и файл `/var/log/upsguard.log` (`RotatingFileHandler`, 1 МБ, 5 копий).
- `wall` для консолей.
- Всплывающее окно в X-сессии best-effort: `notify-send` от имени пользователя сессии, если есть.
- Сбой уведомления никогда не мешает выключению.

## 7. Конфигурация

`/etc/upsguard/upsguard.ini`. Значения ниже это поставляемые по умолчанию. Числовые пороги принимают целое ≥ 0 или `off`.

```ini
[general]
dry_run = yes                 ; поставляемый режим: только пишем в лог, что бы сделали
state_file = /var/lib/upsguard/state.json
log_file = /var/log/upsguard.log

[nut]
host = 127.0.0.1
port = 3493
ups = ups                     ; имя секции из /etc/nut/ups.conf
poll_interval = 2
timeout = 3

[policy]
ob_debounce = 5
ol_stable = 30
monitor_off_after = 120       ; 0 = сразу после начала отключения
shutdown_after = 2700         ; T; стартовое значение, уточняется по фазе 0
shutdown_at_charge = 25       ; %
shutdown_at_runtime = 600     ; с
trigger_hold = 20
shutdown_grace = 90           ; больше ol_stable, иначе отмена невозможна
lb_grace = 10
comms_lost_notify_after = 60

[monitor]
enabled = yes
idle_off_seconds = 60

[notify]
methods = log, wall, desktop
```

`check-config` проверяет диапазоны и предупреждает, если выключены все три правила выключения (тогда ПК выключится только по `LB`) или если `dry_run = yes`.

## 8. Автовозврат ПК (фаза 2)

Выход ИБП рубить нельзя, поэтому сам ИБП ПК не «перезапустит». Механизм: RTC-будильник.

1. Перед `poweroff` политика ставит будильник `rtcwake -m no -s <rtc_interval>` (900 с) и записывает `powered_off_by_policy`.
2. ПК просыпается. При старте демон видит флаг и ждёт данные ИБП до `boot_check_wait` (60 с).
   - `OB`: снова ставит будильник и штатно выключает ПК.
   - Стабильный `OL` (`ol_stable`): снимает флаг, загрузка идёт дальше.
   - Данных нет за `boot_check_wait`: считается, что сеть в порядке (загрузка идёт дальше) и в лог пишется громкое предупреждение. Иначе сломанный NUT при нормальной сети приводил бы к бесконечному циклу «загрузился, выключился».
3. Дополнительно в BIOS включается «Power On» при возврате питания: сработает, если ИБП сам погас.

Параметры (`[wake]`): `strategy = none | rtc` (по умолчанию `none`), `rtc_interval`, `boot_check_wait`.

Цена: каждые `rtc_interval` ПК 1–2 минуты работает на батарее. Средняя добавка нагрузки примерно `P_ПК × t_бодрствования / (t_бодрствования + rtc_interval)`, то есть при 150 Вт, 90 с и 900 с около 14 Вт. Это сопоставимо с нагрузкой самого коммутатора, поэтому `rtc_interval` подбирается опытом в фазе 2, а результат сравнивается с задержкой возврата после восстановления сети (в среднем половина интервала). Формат состояния для фазы 2 готов уже в фазе 1: флаг `powered_off_by_policy` пишется с самого начала.

Альтернативы, которые стоит оценить в фазе 2, если RTC окажется слишком дорогим: suspend-to-RAM вместо полного выключения (пробуждение за секунды, потребление единицы ватт), Wake-on-LAN с постоянно живого устройства.

## 9. Упаковка и развёртывание (офлайн)

Бандл (по образцу upsmonitor): `debs/` (NUT и зависимости, набранные `apt-get download` на самой целевой машине), `upsguard/` (код), `conf/` (шаблоны `nut.conf`, `ups.conf`, `upsd.conf`, `upsguard.ini`), `upsguard.service`, `install.sh`, `uninstall.sh`.

`install.sh` идемпотентный:

1. `dpkg -i debs/*.deb`.
2. Пишет `nut.conf` (`MODE=standalone`), `ups.conf` (`driver = usbhid-ups`, `port = auto`, `vendorid`/`productid` из `lsusb`; если устройство `05dd:*` не найдено, установка останавливается с понятным сообщением), `upsd.conf` (`LISTEN 127.0.0.1 3493`).
3. Маскирует `nut-monitor.service` и удаляет флаг `POWERDOWNFLAG`, если он есть.
4. Копирует код в `/opt/upsguard`, конфиг в `/etc/upsguard`, ставит `upsguard.service`.
5. Включает и запускает `nut-driver`, `nut-server`, `upsguard`.

Юнит `upsguard`: `After=nut-server.service`, `Restart=always`, `RestartSec=5`, `ExecStart=/usr/bin/python3 /opt/upsguard/upsguard.py --config /etc/upsguard/upsguard.ini`.

Ни pip, ни venv: только системный Python 3.7 и stdlib. Чистые `.py` без бинарников (замкнутая программная среда и контроль целостности на площадке). Поставляемый `dry_run = yes` не даёт первому запуску на боевой машине устроить сюрприз.

## 10. Тестирование

**На Windows-машине разработки** (`pytest`, Python 3.7):

- `policy` с фейковыми часами: короткая просадка короче `ob_debounce`; отключение, монитор, возврат; выключение по T, по заряду, по остатку; `LB`; мигающая сеть; потеря связи при `OB`; перезапуск демона с восстановлением состояния; повторные срабатывания; устаревшее состояние (другой `boot_id`).
- `nutclient` против фейкового `upsd` на сокете: форматы ответов, обрыв соединения, таймаут.
- `actions` с подменой `runner`: проверка командных строк `xset`, `wall`, `notify-send`, `systemctl`.
- `config`: диапазоны, `off`, неизвестные ключи.

**На целевой машине:**

1. `upsc ups` видит ИБП.
2. NUT `dummy-ups` проигрывает отключение; демон в `dry_run` пишет лестницу в лог.
3. Реальный тест в окно обслуживания: выдернуть вход ИБП под реальной нагрузкой, сначала с маленьким T.

## 11. Этапы и критерии готовности

**Фаза 0 (без нашего кода, делает пользователь):**

```
lsusb
apt-cache policy nut-server nut-client
sudo rtcwake -m off -s 120
```

Далее: собрать `debs/`, поставить NUT, снять `upsc ups`; посмотреть в BIOS «Restore on AC Power Loss» и опцию RTC-пробуждения; понаблюдать «Battery Save» (нагрузка на ИБП только сетевое оборудование, сеть на входе ИБП отключена, ждать 35 минут); записать реальные `ups.load`, `ups.realpower`, `battery.runtime` с включённым и выключенным ПК. Результат: подтверждённые `vendorid`/`productid` и данные для выбора T.

**Фаза 1, готово, когда:**

- тесты проходят;
- на целевой машине при `dry_run = no` лестница отрабатывает на реальном отключении: монитор гаснет и восстанавливается, ПК выключается по T, возврат сети до T отменяет выключение;
- `install.sh`/`uninstall.sh` идемпотентны, повторный запуск ничего не ломает.

**Фаза 2, готово, когда:** после выключения политикой ПК сам включается в пределах `rtc_interval` после возврата сети и не загружается полностью, пока сеть отсутствует.

## 12. Риски и запасные пути

| Риск | Запасной путь |
|---|---|
| NUT не видит GES302 (другой PID или UART-мост) | `nutdrv_qx` по DB9-порту через USB-serial; либо свой транспорт поверх pyusb (вариант C из обсуждения) |
| Fly, SCADA или Astra SE мешают DPMS | `xrandr --output <имя выхода> --off`; либо только выключение ПК без гашения монитора |
| «Battery Save» гасит ИБП при малой нагрузке | Подключить к ИБП дополнительную нагрузку или изменить схему. Решается по результатам фазы 0. |
| Демон завис или упал | `Restart=always`, все внешние вызовы с таймаутами. Пока демон мёртв, ПК не выключится (сейчас без демона так же). |
| RTC-пробуждение не поддерживается BIOS | Wake-on-LAN с постоянно живого устройства или ручное включение |
| Устаревший `/etc/killpower` отрубит ИБП при выключении | `install.sh` удаляет флаг, демон предупреждает в `status` и в логе при его наличии |
