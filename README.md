# upsguard: Delta GAIA и два АРМ

[![CI](https://github.com/ixarek/upsguard/actions/workflows/ci.yml/badge.svg)](https://github.com/ixarek/upsguard/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Служба на Python для Linux (Astra Linux 1.8): следит через NUT за ИБП Delta GAIA и при работе от батареи штатно выключает или усыпляет рабочие места, не трогая сам ИБП. Лицензия проекта — MIT. В `debs/` лежат неизменённые пакеты NUT и библиотек из репозитория Astra Linux для офлайн-установки (свои лицензии, источники и хэши — в `debs/MANIFEST.tsv`).

Проверено по текущему коду и конфигам 2026-09-30. Основной переключатель — `[general] action_mode`; в поставляемых INI стоит `off`. Отдельный `rtc_mode` нужен только для чтения старых конфигов.

АРМ1 `sikn-531` (Astra Linux 1.8) подключён к Delta GAIA 3 кВА по USB. На нём уже работают NUT `usbhid-ups`, `upsd` и `upsc delta@localhost`. АРМ2 получает показания по сети от `upsd` АРМ1; на АРМ2 NUT устанавливать не нужно. Программа использует только чтение и **никогда не подаёт команды отключения выхода ИБП**: после выключения АРМ он продолжает питать сетевое оборудование.

## Выбор действия

Выбираются отдельно на каждом АРМ в `conf/upsguard.ini` **в папке программы** параметром `action_mode`. Если папка находится в `~/upsguard`, рабочий файл — `~/upsguard/conf/upsguard.ini`.

| Режим | Реакция на работу ИБП от батареи (`OB`) | При возврате `OL` |
|---|---|---|
| `off` | После подтверждения `OB` при заряде **50 % и ниже** непрерывно 20 с предупреждает и ждёт **120 с**, затем выполняет `rtcwake -m off -s 900` для штатного выключения. `LB` запускает отсчёт `lb_grace`. | Устойчивый `OL` в течение 30 с отменяет ожидающее выключение. |
| `mem`, `disk`, `standby`, `freeze` | После того же порога и задержки переводит АРМ в выбранный режим сна через `rtcwake`. | После пробуждения проверяет ИБП; при устойчивом `OL` оставляет АРМ работать, при `OB` снова даёт 120 с и усыпляет. |
| `monitor_only` | Через 5 с устойчивого `OB` гасит монитор; АРМ и его программы продолжают работу. Повторяет гашение раз в 30 с, если мышь или программа включила экран. | Через 30 с устойчивого `OL` включает монитор обратно. |

Порог `charge_percent = 50`, пауза `shutdown_grace = 120`, `lb_grace = 120`, интервал `wake_interval = 900` (15 минут), `action_mode` и способ работы с экраном регулируются **в конфиге каждого АРМ**. После правки проверьте `check-config` и перезапустите `upsguard.service`. Команда `status` показывает **текущий файл INI** и показания ИБП; параметры уже работающей службы видны в журнале при её запуске. Режим `monitor_only` не ставит RTC и не выключает АРМ даже при `LB`.

Если отсчёт уже запущен, появление `LB` не продлевает его: действует более ранний срок. Потеря свежих данных отменяет отсчёт; в `monitor_only` она также восстанавливает погашенный программой монитор. Возврат заряда выше порога сам по себе уже начатый отсчёт не отменяет.

## Команда RTC в INI

В секции `[general]` параметр `action_mode` выбирает и действие, и аргумент `-m` команды `rtcwake -m <action_mode> -s <wake_interval>`. Интервал задаётся в `[policy]` и отсчитывается **после** задержки `shutdown_grace`. Выбор делается отдельно на каждом АРМ.

| `action_mode` | Что происходит |
|---|---|
| `off` (по умолчанию) | `rtcwake -m off -s 900` ставит будильник и вызывает штатное выключение. |
| `mem` | `rtcwake -m mem -s 900`: сон с сохранением памяти, затем пробуждение и проверка ИБП. |
| `disk` | Гибернация, если она настроена и работает на этом АРМ. |
| `standby`, `freeze` | Менее глубокие режимы сна, если они поддерживаются АРМ. |
| `monitor_only` | Только мониторы, команда RTC не выполняется. |
| `no` | Дополнительный вариант: установить RTC-будильник, затем выполнить `systemctl poweroff`. |

Пример сна на одном АРМ:

```ini
[general]
action_mode = mem

[policy]
wake_interval = 900
```

Это отдельные строки в существующих секциях файла `conf/upsguard.ini`, а не полный новый конфиг. На уже установленном АРМ сначала обновите программу по инструкции ниже, затем измените **одну** строку `action_mode` (в старом INI может стоять `poweroff`) на нужный режим, запустите `check-config` и перезапустите службу. Установщик использует этот же INI и сохраняет его параметры действия. Старые сочетания `action_mode = poweroff` с `rtc_mode = no/off` и `action_mode = sleep` с `rtc_mode = mem/disk/standby/freeze` поддерживаются: новое значение `action_mode = off/mem/...` имеет приоритет над оставшейся старой строкой `rtc_mode`. Её можно удалить при следующем редактировании. Произвольную строку shell-команды в INI программа не исполняет.

Проверьте на конкретном АРМ `cat /sys/power/state` и `cat /sys/power/mem_sleep`. `rtcwake --list-modes` перечисляет режимы утилиты, а `/sys/power/state` — режимы, доступные ядру на этой машине. Если в `mem_sleep` есть только `s2idle`, `mem` использует тот же сон, что `freeze`; выбрать `deep` при его отсутствии нельзя. `standby` можно использовать только при наличии этого слова в `/sys/power/state`. Описание ядра: https://docs.kernel.org/admin-guide/pm/sleep-states.html.

На испытанном АРМ пользователь подтвердил выключение `off` и вход в гибернацию `disk`. Для `mem` доступен только `s2idle`; снижение измеренной нагрузки составило около 10 Вт из 180 Вт. `freeze` дал такой же результат; `standby` отсутствует в списке доступных состояний. Повторите проверку на АРМ2: поддержка зависит от машины. Вход в гибернацию и успешное восстановление по RTC проверяются отдельно. При ошибке RTC или перехода в сон служба оставляет АРМ включённым, записывает ошибку и показывает её в окне, если доступен X11.

## Повторное включение после выключения или сна

Перед своим выключением **каждый АРМ** ставит RTC-будильник (по умолчанию `rtcwake -m off -s 900`). Через 15 минут он включается и получает свежие данные: АРМ1 читает USB/NUT, АРМ2 опрашивает NUT АРМ1 по сети. Основная служба сначала выполняет проверку RTC-загрузки, затем переходит к обычному мониторингу. Если есть стабильный `OL` (30 с), АРМ остаётся включённым. При `OB` вновь начинается **120-секундный отсчёт**; за это время можно остановить службу и отменить выключение. Перед командой выключения выполняется ещё один опрос. Затем АРМ ставит следующий будильник и выключается. В режимах сна действует тот же принцип, но возвращается прежняя ОС и работа службы продолжается после пробуждения.

Выключенный АРМ не может получить USB-событие в момент перехода ИБП в `OL`; он узнает о возврате питания при следующем RTC-пробуждении. Срок до включения — до одного интервала `wake_interval` плюс загрузка и подтверждение `OL`. Каждая контрольная загрузка при продолжающемся `OB` расходует часть батареи.

**При отсутствии достоверных показаний никто не выключается.** На АРМ1 физически проверяется USB-устройство `05dd:041b` до и после каждого опроса. На АРМ2 потеря сети, `upsd` или ответ NUT `DATA-STALE` отменяют отсчёт. При USB-отключении `upsd` обычно помечает данные устаревшими за 15 с; поэтому 120-секундная задержка оставляет время на обнаружение пропажи. Как у любого сетевого опроса, остаётся короткое окно между последним успешным ответом и самой командой `poweroff`; это проверяется на площадке.

Если АРМ2 проснулся, пока АРМ1 ещё выключен или уже снова выключился, АРМ2 **останется включённым**: у него нет свежих данных, а принимать решение по старому `OB` запрещено. Для гарантированного совместного цикла двух выключенных АРМ нужна синхронизация пробуждений (например, WoL от АРМ1 к АРМ2) и проверка доступности АРМ1 в окно загрузки. Это отдельная аппаратная проверка до боевого включения на АРМ2.

В режимах сна АРМ1 тоже не отвечает АРМ2 по сети. Если АРМ2 проснулся раньше АРМ1, отсутствие свежих данных оставит его работающим до восстановления связи. Сон сам по себе не устраняет необходимость согласовать их пробуждение.

## Установка

Исходные показания на `sikn-531`: `ups.status: OL`, `battery.charge: 100`, `battery.runtime: 7239`, `ups.load: 10.0`, `ups.realpower: 202.0`. Имя рабочей секции — `[delta]`; старое `[ups]` из раннего плана не использовать. В комплекте 11 пакетов NUT, включая `libusb-1.0-0-dev`, который потребовался для `nut-scanner -U` на этой машине. Уже установленный NUT повторно ставить не нужно.

1. На АРМ1 скопировать папку проекта и выполнить из неё:

   ```sh
   sudo ./install.sh --role master
   sudo python3 upsguard/upsguard.py status
   ```

2. Для АРМ2 на АРМ1 разрешить NUT слушать адрес АРМ1. В `/etc/nut/upsd.conf` сохранить `LISTEN 127.0.0.1 3493` и добавить `LISTEN <IP_АРМ1> 3493`; затем `sudo systemctl restart nut-server.service`. `MAXAGE` оставить стандартным (15 с) либо не выше 30 с: от этого зависит, как быстро АРМ2 перестанет получать старые данные при потере USB. Доступ к TCP/3493 открыть **только с IP АРМ2** в действующем файрволе. Проверить на АРМ1: `upsc delta@<IP_АРМ1> ups.status`.

3. На АРМ2 скопировать папку проекта и выполнить:

   ```sh
   sudo ./install.sh --role client --master-ip <IP_АРМ1>
   sudo python3 upsguard/upsguard.py status
   ```

Программа запускается прямо из этой папки. Установщик создаёт системные службы с абсолютными путями к `upsguard/upsguard.py` и `conf/upsguard.ini`; копий кода в `/opt` и конфигурации в `/etc` больше нет. По умолчанию ручные команды находят тот же INI относительно файла программы, независимо от текущего каталога. `--config` позволяет явно выбрать другой INI для ручного запуска. Команды `check-config`, `status` и журнал запуска службы показывают полный путь прочитанного файла.

При установке `--role` задаёт роль в этом же рабочем INI; на клиенте `--master-ip` задаёт адрес NUT. При переводе клиента в мастер адрес меняется на локальный. Остальные параметры, русские комментарии, права и владелец INI сохраняются. На АРМ1 установщик не переписывает NUT, но маскирует `nut-monitor.service` (`upsmon`), чтобы штатный сценарий NUT не отключил выход ИБП. Если найден `/etc/killpower`, установка останавливается до выяснения причины. На АРМ2 `.deb` и `upsmon` не нужны.

Папка должна оставаться на своём месте и быть доступна при загрузке. После переноса папки снова выполните `install.sh`: он обновит пути в службах. Шаблоны из `systemd/` вручную не копируйте — пути подставляет установщик. Службы работают от root для RTC и выключения; размещение INI в `/etc` для доступа не требуется. Файлы состояния `/var/lib/upsguard/state.json`, журнала `/var/log/upsguard.log` и блокировки `/run/upsguard/lock` нужны для восстановления после пробуждения, диагностики и исключения одновременных действий служб.

`install.sh` не устанавливает пакеты из `debs/`, не меняет `LISTEN` и не настраивает файрвол: NUT на АРМ1 должен быть подготовлен заранее. При установке скрипт отключает старый автозапуск `upsguard-bootcheck.service` и перезапускает `upsguard.service`. Проверка загрузки теперь выполняется внутри основной службы: рабочий стол может запуститься во время этой проверки и показать окно с таймером. Отдельный юнит boot-check сохранён для совместимости и ручной диагностики при остановленной основной службе; включать его автозапуск не нужно.

В обоих **поставляемых образцах** стоит `dry_run = yes`: логика и диагностика работают, но RTC, выключение, сон и реальное гашение экрана не выполняются. При обновлении значение берётся из уже существующего INI и может быть `no`. Проверить:

```sh
sudo python3 upsguard/upsguard.py check-config
sudo python3 upsguard/upsguard.py status
sudo journalctl -u upsguard.service -u upsguard-bootcheck.service -f
```

Оба образца INI сохранены в UTF-8: русские пояснения находятся отдельной строкой **над каждым параметром**. Сообщения службы и установщика выдаются латиницей, чтобы терминал и журнал оставались читаемыми даже при несовпадении кодировок. Для просмотра и редактирования русских комментариев выберите UTF-8 в редакторе MobaXterm и настройках SSH-терминала; на АРМ проверьте `locale` (например, `LANG=ru_RU.UTF-8` либо `LANG=C.UTF-8`, если такая локаль установлена).

Остановка во время отсчёта: `sudo systemctl stop upsguard.service upsguard-bootcheck.service` на нужном АРМ. Для возобновления: `sudo systemctl start upsguard.service`. После проверки поменять `dry_run = no` в конфиге **каждого** АРМ и выполнить `sudo systemctl restart upsguard.service`.

Для `monitor_only` убедиться, что используется X11, и при необходимости заполнить `[display] name = :0` и `xauthority = /полный/путь/к/Xauthority`. `backend = auto` пробует X11 при наличии X-сокета, иначе консольный `/sys/class/graphics/fb0/blank`. В графической сессии требуется утилита `xset`. На площадке проверить фактический экран: пока монитор не подключён, физическое гашение проверить нельзя.

## Сообщение и таймер на мониторе

В `[display]` по умолчанию `popup = yes`. В режимах выключения и сна окно появляется после подтверждения `OB`: показывает заряд, выбранное действие и оставшееся время. До достижения порога таймер показывает «—». После возврата `OL` показывает подтверждение питания, затем закрывается; при потере свежих данных окно закрывается вместе с отменой отсчёта. После ошибки действия появляется причина и отсчёт до следующей попытки. При `dry_run = yes` окно тоже работает, с пометкой пробного режима.

- **Остановить службу**: немедленно отменяет отсчёт, очищает сохранённое решение и останавливает обе службы UPS Guard на этом АРМ. Для возобновления — `sudo systemctl start upsguard.service`.
- **Скрыть окно** или крестик: скрывает сообщение до следующего отключения питания. Отсчёт и действие продолжаются.
- `popup = no` отключает окно. `wall` отдельно управляет сообщениями в терминалах. В режиме `monitor_only` окно не открывается, поскольку экран гасится при `OB`.

Без отключения питания и без обращения к ИБП проверить окно на 30 секунд:

```sh
cd ~/upsguard
sudo python3 upsguard/upsguard.py test-popup
```

Эта команда не выполняет RTC, сон, выключение или остановку службы даже при `dry_run = no`. В ней кнопка остановки заменена на «Закрыть проверку». Тест можно запустить одновременно со службой.

Окно использует X11, системные `libX11.so.6` и `libcairo.so.2`, без дополнительных Python-пакетов. Дисплей и доступ задаются существующими `name` и `xauthority`; при пустом `xauthority` программа ищет файл `-auth` процесса Xorg. Если рабочего стола ещё нет или доступ к X11 закрыт, служба продолжает диагностику и пытается открыть окно раз в 15 секунд; причина видна в журнале. После RTC-загрузки таймер начинается с подтверждения `OB`, независимо от того, когда появился рабочий стол. В консольном режиме и в сессии без X11 графического окна нет.

## Обновление программы и применение настроек

При обновлении сохраняйте свой `conf/upsguard.ini`: распаковка нового архива с заменой этого файла сбросит ваши настройки. Например, если программа находится в `~/upsguard`, распакуйте архив из домашней папки с исключением рабочего INI:

```sh
cd ~
unzip -o /путь/к/upsguard.zip -x 'upsguard/conf/upsguard.ini'
cd ~/upsguard
sudo ./install.sh --role master
```

Для АРМ2 последняя команда — `sudo ./install.sh --role client --master-ip <IP_АРМ1>`. После обновления источником настроек становится **INI в этой папке**, включая уже сделанные там изменения. Старые `/etc/upsguard/upsguard.ini` и `/opt/upsguard/upsguard.py`, если они остались от прежней версии, не используются и автоматически не удаляются. Если нужные настройки были только в старом INI, перенесите их в `conf/upsguard.ini` до установки.

После изменения действующего INI на нужном АРМ:

```sh
cd ~/upsguard
nano conf/upsguard.ini
sudo python3 upsguard/upsguard.py check-config
sudo systemctl restart upsguard.service
sudo journalctl -u upsguard.service -n 20 --no-pager
```

Перезагрузка АРМ не нужна; `daemon-reload` требуется при изменении файлов `.service`, а не INI. Конфиг читается один раз при запуске процесса. При сохранённом отсчёте перезапуск с тем же `action_mode` продолжит его; смена `action_mode` начинает новое подтверждение порога и новую задержку. Переход с `dry_run = yes` на `no` при уже истёкшем отсчёте может выполнить действие сразу после свежего подтверждения `OB`, поэтому пробный режим отключайте после проверки текущего состояния.

Состав проекта и фактическая логика описаны в `docs/superpowers/specs/2026-09-29-upsguard-design.md`. Этот файл обновлён по реализации; старые будущие функции больше не приводятся в нём как работающие.

## Проверка перед боевым режимом

- Сначала проверить `dry_run` и показания на обоих АРМ, затем в окно обслуживания отключить **вход** ИБП и посмотреть `OB`; выход ИБП не отключать.
- В процессе 120-секундного ожидания отключить USB на АРМ1: оба АРМ должны отменить отсчёт; вернуть USB и проверить восстановление чтения. Проверить также отключение сети АРМ2.
- Проверить `test-popup`, окно реального отсчёта и кнопку остановки на экране каждого АРМ; проверить появление окна после RTC-загрузки, когда запускается рабочий стол.
- Для `off` проверить пробуждение обоих АРМ из S5. На АРМ1 ранее проверялось `rtcwake -m off -s 120`; АРМ2 нужно испытывать отдельно. Для старого режима `no` отдельно проверить его сочетание с `systemctl poweroff`.
- При выборе `mem`/`disk`/`standby`/`freeze` проверить штатное RTC-пробуждение, повторное двухминутное ожидание при `OB` и отмену при выдернутом USB. Сон расходует больше энергии, чем полное выключение; фактическое потребление зависит от обоих АРМ.
- При `monitor_only` проверить `OB`/`OL`, ручное включение монитора мышью, восстановление после остановки службы и права X11.

Разработческие проверки: `python3 -m unittest discover -s tests -v`, затем `cd debs && sha256sum -c SHA256SUMS`. Они не заменяют тест физического USB, RTC и экранов. Снятие служб: `sudo ./uninstall.sh`; конфиг, состояние и журнал остаются для диагностики.
